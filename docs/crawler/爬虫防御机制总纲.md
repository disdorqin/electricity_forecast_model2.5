# 爬虫防御机制总纲（边界条件治理）

> 日期：2026-09-27｜2026-10-10 状态复核：**P0/P1 中一部分已实施并进入 V10-r11 / AUX 当前入口**。`apps/*` + `resilience/*` 已承担 preflight、健康检查、profile/孤儿浏览器治理、根因诊断和 doctor；其余未接入项仍按本文作为候选设计，不能因为文件存在就宣称全部上线。
> 背景：基本功能已完成，但边界条件处理不足，长跑/定时场景不稳定。
> 本文 = 业界先例调研 + 本项目现状对照 + 防御机制提案（分层、带优先级与风险）。当前真实依赖与发布状态以 `CODEGRAPH_爬虫源码全局关系图.md` 和版本台账为准。

## 一、业界先例调研结论

### 1.1 通用容错模式（已被大规模生产验证）

| 模式 | 要点 | 代表来源 |
|---|---|---|
| **指数退避 + 抖动** | 2-5s → 8-15s → 30-60s，加随机 jitter 防重试风暴 | Decodo / Scrapfly |
| **熔断器 Circuit Breaker** | CLOSED→OPEN→HALF-OPEN；失败率超阈值（如 5 分钟 >50%）直接快速失败，冷却后半开探测 | Scrapfly (`pybreaker`) / EasyParser |
| **幂等写入** | 唯一键 + upsert，重复处理不产生脏数据 | 业界共识（我们已有） |
| **死信队列 DLQ** | 反复失败的任务移出主队列，避免毒化主流程，且可人工复查 | Node crawler 架构文 |
| **检查点 / 断点续跑** | 原子写 state 文件（`tmp` + `os.replace`），崩溃后可恢复 | StudyRaid |
| **自适应限流** | 滚动成功率 <95% 降并发 20%；延迟 2x 基线则减速 | Decodo |
| **优雅关闭** | 捕获 SIGTERM，完成当前任务再退出，防止半成品 | Node crawler 架构文 |
| **漂移检测** | 对比 known-good baseline，DOM 改版时告警（而非静默产出错误数据） | Decodo |
| **错误隔离** | 单条失败不影响批次其余项 | EasyParser bulk |

### 1.2 浏览器/CDP 层特有机制（与我们的故障高度吻合）

**① SingletonLock 死锁机制**（关键）
- Chrome 用 `SingletonLock` / `SingletonSocket` / `SingletonCookie` 保证同一 `--user-data-dir` 单实例。
- 正常退出会自行清理；**`kill -9` / pkill / 崩溃强杀**来不及清理 → 下次启动检测到残留锁，
  认为目录被占用 → **调试端口卡死**（表现为"启动了但连不上"）。
- → 这解释了我们的 `browser.bootstrap_launcher_exited code=0` 与「20s 未打开可控页面」。

**② CDP 绑定的是单个 target，不是浏览器**
- 导航 / 重定向 / 新开标签会销毁旧 target，原 websocket 指向已不存在的页面
  → 表现为「卡住 / 超时 / 对着已关闭的页面继续操作」。
- → 对应我们的 `Inspected target navigated or closed`（r11d 已做容忍重试）。

**③ CDP 启动超时不能只加超时，要有恢复路径**
- 复盘结论：机器繁忙时 Chrome 冷启动远超预期（15s 默认不够）。
- 有效做法：**延长启动 deadline（15s→45s）**；失败时**先清理占用端口/profile 的残留进程，再重试一次**；
  并记录启动耗时分布（长尾与开发环境完全不同）。
- → 我们固定 20s + 无进程治理，正好踩在这两条上。

**④ 专用 profile + 固定 debug port 是最稳的自动化形态**
- 相比"复用日常 profile"，专用 `--user-data-dir` 登录一次即持久、无需每次授权、沙箱下更可靠。
- 建议：**首个工具调用前先做一次健康检查**（列 targets / 截图）；每次大导航后重新校验 URL。
- → 我们已是专用 profile（正确），但**缺启动前健康检查**。

## 二、本项目现状对照

| 能力 | 状态 | 说明 |
|---|---|---|
| 幂等 upsert | ✅ 已有 | 唯一键 `market_date+时段+unit_id` / AUX 请求键 |
| 三层防护认证（复用→重开→轮换） | ✅ r11f 已有 | 含页面失效自动刷新 |
| 浏览器死亡自愈 | ✅ r11f 已有 | CDP 端口不可达 → 触发重认证（原为静默白跑） |
| 错误隔离（单源失败不影响整批） | ✅ 已有 | `all-designed` sweep continue |
| 结构化日志 / 阶段报告 | ✅ 已有 | `report.json` + `stages`/`events` |
| **进程与锁文件治理** | ❌ **无** | 只诊断不治理（`bootstrap_profile_maybe_locked` 仅打日志） |
| **启动前健康检查** | ❌ 无 | 直接 bootstrap |
| **bootstrap 超时自适应** | ❌ 固定 20s | 业界建议忙机 45s |
| **指数退避 + 抖动** | ❌ 固定 6s sleep | 无退避、无抖动 |
| **全局熔断器** | ❌ 无 | 仅"连续 3 次"计数，无冷却/半开 |
| **自动断点续跑** | ❌ 手工算 `--date/--lookback` | 每次中断都要人工查库 |
| **失败日期待补清单（DLQ）** | ❌ 无 | 失败日期无人记录，易漏 |
| **锁冲突重试（96 被 AUX 挡）** | ❌ 无 | 直接 `RUN_ALREADY_ACTIVE` 跳过、不重试 |
| **404 / 空数据分类** | ⚠️ 部分 | 未区分"该日无数据(正常)" vs "接口路径错(异常)" |
| **数据完整性校验** | ⚠️ 部分 | 有 96 点完整性，但缺跨表/跨日告警 |

## 三、用户提出的四个脆弱点 → 逐条对应

| 脆弱点 | 根因 | 现有 | 提案 |
|---|---|---|---|
| 1. cookie 失效就失败 | 复用时无后端存活探测；失效后不会刷新 | r11f 已加 D1 判据 + 自动刷新 | + 采集前**轻量探活**（P1） |
| 2. 浏览器经常连不上 | 残留进程 → SingletonLock；CDP target 失效；冷启动慢 | 仅诊断 | **P0 进程治理 + bootstrap 45s** |
| 3. 登录后部分网页 404 | 接口路径/日期无数据/权限 混杂 | 统一记 FAILED | **P1 错误分类**（正常空 vs 真异常）+ DLQ |
| 4. 残留进程导致 profile 锁 | 强杀/崩溃未清理 | 仅诊断 | **P0 清理 Singleton* + 可选杀残留进程** |

## 四、防御机制提案（分层）

### L0 进程与环境治理 —— **P0，收益最大**

| # | 机制 | 说明 | 风险 |
|---|---|---|---|
| L0-1 | **启动前清理 Singleton\* 锁文件** | 当目标 profile 目录存在 `SingletonLock/Socket/Cookie` **且无活进程持有**时自动删除 | 低 |
| L0-2 | **可选：清理残留浏览器进程** | 仅清理命令行含 `--user-data-dir=<我们的 profile>` 的进程 | ⚠️ **中**（可能误杀用户手动打开的浏览器，需讨论） |
| L0-3 | **启动前健康检查** | 先探测已有 CDP 端口是否可控（列 targets），健康则直接复用 | 低 |
| L0-4 | **bootstrap 超时 20s → 45s（可配）** | 忙机冷启动长尾 | 低 |
| L0-5 | **失败后"清进程 → 重试一次"** | 业界验证做法，只重试一次 | 低 |

### L1 认证韧性 —— 已做三层，增强项 P1
- L1-1 采集前轻量探活（避免带失效 cookie 跑到首源）
- L1-2 记录登录耗时指标（长尾监控）

### L2 网络与请求层 —— P0/P1
- **L2-1 指数退避 + 抖动**（替固定 6s）【P1】
- **L2-2 全局熔断器**【P0】：连续 N 次失败 → 冷却 T 秒；冷却后单次探测（HALF-OPEN）。
  直接解决「浏览器死后每个源 2s 超时刷屏几百行」的观感与资源浪费。
- L2-3 错误分类：网络 / 认证 / 业务空 / 服务端错误 / 404，分别计数与处置【P1】

### L3 数据层 —— P0/P1
- **L3-1 自动断点续跑**【P0】：读库里最早日期，自动算 `--date/--lookback`，中断后直接重跑
- L3-2 失败日期 DLQ（写入 pending 文件，下次优先补）【P1】
- L3-3 数据完整性校验（每天应有 96 点；缺则告警）【P2】

### L4 调度与并发 —— P0
- **L4-1 锁冲突重试**【P0】：96 被 `RUN_ALREADY_ACTIVE` 挡住 → 等待重试（bat 包装或内置）
- L4-2 stale lock 自动释放（进程已死但锁文件残留）【P1】
- L4-3 96/AUX 错峰（或分离锁 + 独立 profile）【P2，需评估】

### L5 可观测与告警 —— P1/P2
- L5-1 关键指标（登录耗时、成功率、日行数、失败分类计数）
- L5-2 异常摘要（每次 run 输出一段"哪里失败、为什么"的结构化结论）

## 六、待讨论决策点（需你拍板）

1. **L0-2 是否允许自动杀残留浏览器进程？**
   - 允许：最省事，但可能关掉你/同事手动打开的 Chrome（可通过只杀"命令行含我们 profile"来规避大部分）。
   - 仅清理锁文件 + 告警：最安全，但残留进程仍会占锁。
   - 折中（推荐）：默认**只清锁文件**；另提供 `--force-clean-browser` 开关显式启用杀进程。
2. **bootstrap 超时 20s 提到多少？** 建议 45s（业界忙机经验值）；若嫌单次失败太慢可设 30s。
3. **熔断器阈值**：连续失败几次、冷却多久？建议源级连续 5 次 → 冷却 60s，且整 run 失败率 >50% 则中止。
4. **96 定时任务包装**：做 bat 外层重试，还是内置到 exe？内置更稳但两个 exe 都要改。
5. **是否把防御机制也同步给 96？** 目前三层防护只做了 AUX；96 是否同步（成本：需重打包 + 真机验证）。
