# 矩阵计算底层优化调研报告（cuBLAS / cuDNN / CUTLASS / BLAS）

> 日期：2026-08-15　作者：opencode　主题：从矩阵计算层加速 GPU 模型（TimeMixer/RT916）训练
> 背景约束：序列长度短（96 点）、hidden_dim 中等（64~128）、batch 小；GPU 云为 RTX3090（Ampere, sm86）；CPU 本机为 conda epf-2（CPU only）。
> 方法：webfetch 权威源（NVIDIA cuBLAS/cuDNN/CUTLASS 官方文档、NVIDIA Deep Learning Performance 指南、PyTorch 性能调优指南）+ 本项目代码热点核验。

---

## TL;DR 结论

1. **本项目 GPU 模型的 GEMM 全是"小矩阵"**（≈ `batch×64×64`），属于 **memory-bound + launch-overhead bound**，不是 compute-bound。cuBLAS 算法选择、CUTLASS 定制在此场景收益极小。
2. **TF32 / BF16 AMP 已由 `optim/perf_knobs.py` 打开**，这已是矩阵层能拿到的最大头收益；剩余收益来自**减少 kernel 启动开销 + 算子融合**，即 `torch.compile`（reduce-overhead / CUDA Graph），而不是换底层库。
3. **CUTLASS 不值得上**。它是为"大 GEMM 逼近硬件峰值 + 定制 epilogue"设计的；本项目 64×64 GEMM 的瓶颈是 launch 与访存。Triton（torch.compile 的默认后端）是"免费午餐"，先吃它。
4. **CPU 侧**：numpy/pandas 特征工程是 CPU 大头，BLAS 线程调优（`OMP_NUM_THREADS`）是低成本锦上添花；LightGBM 不走 BLAS，无关。
5. 结合已有结论（skill §4.3/4.4）：矩阵层的总收益预计远小于**特征预计算 + warm-start 续训**（3天→1天），应保持"矩阵层做基础项，加速主线放特征/续训"的优先级。

## 1. cuBLAS / cuDNN 使用与调优

### 1.1 PyTorch 何时用 cuBLAS GEMM、何时用 cuDNN

| 算子 | 底层库 | 本项目对应位置 |
|---|---|---|
| `nn.Linear` / `addmm` / `mm` / `bmm` / `einsum` | **cuBLAS（Ampere+ 实际走 cuBLASLt）** | TimeMixer 所有 `past_proj`/`future_mixer`/`head`/`season_mlps`；RT916 的 `embedding`/`delta_head`/`gate_net`/`out_proj` |
| `nn.Conv1d` / `Conv2d`（含 dilation） | **cuDNN**（内部多为 implicit GEMM 实现） | RT916 的 `SpikeResidualBranch`（3 个 dilation Conv1d）、`InceptionBlockV1`（6 个 Conv2d）；TimeMixer/TimesNet 的 `InceptionBlock1D` |
| `torch.fft.rfft` | **cuFFT**（非 cuBLAS/cuDNN） | RT916 `FFT_for_Period`、`DynamicPeriodGate._period_features` |
| `AvgPool1d` / `interpolate` / `LayerNorm` / `Dropout` | PyTorch 自带算子（memory-bound） | TimeMixer `MovingAvg`/`PastDecomposableMixing`；所有 LayerNorm |

要点：
- 卷积（如 `InceptionBlockV1` 的 6 个不同 kernel_size 的 `Conv2d`）由 cuDNN 通过 **implicit GEMM** 实现，本质仍是 GEMM，所以"矩阵层优化"对 conv 同样成立。
- PyTorch 2.x 在 Ampere+ 上 `Linear` 默认走 **cuBLASLt**（支持 heuristics + 用户可配 `cublasLtMatmulPreference`），不再是旧 `cublasSgemm`。[cuBLAS 文档 §3](https://docs.nvidia.com/cuda/cublas/index.html#using-the-cublaslt-api)
- `torch.backends.cudnn.benchmark=True` 让 cuDNN 对 conv 做 autotune（`perf_knobs.py` 已开）。注意：**autotune 对小输入尺寸收益有限，且输入尺寸多变时反而有开销**。[PyTorch Tuning Guide](https://pytorch.org/tutorials/recipes/recipes/tuning_guide.html#enable-cudnn-auto-tuner)

### 1.2 `allow_tf32` / `fp32_precision` 的收益

- **TF32**：Ampere+ 上把 FP32 输入截成 10bit 尾数做 Tensor Core 乘加，FP32 累加。官方基准（A100, 10240×10240 matmul）：开 TF32 ≈ 0.016s vs 关 ≈ 0.11s，**约 7 倍**；相对误差 0.0022 vs 0.00004。[PyTorch CUDA notes](https://docs.pytorch.org/docs/stable/notes/cuda.html)
- **关键限定**：7 倍收益是**大 GEMM（compute-bound）**才成立。本项目 GEMM 是 memory-bound，TF32 收益会显著缩水（访存不变，只省了算力，而算力本来就没用满）。
- **API 换代**：PyTorch 2.9+ 起 `allow_tf32` 已废弃，改用细粒度 `torch.backends.fp32_precision` / `cuda.matmul.fp32_precision` / `cudnn.fp32_precision`（值 `"ieee"` / `"tf32"`），新老 API 不能混用。本项目 `perf_knobs.py:40-41` 用的还是老 API，建议迁移。
- **BF16 已开**：`perf_knobs.py` 默认 `OPTIM_AMP_DTYPE=bf16` + autocast。BF16 直接走 Tensor Core，比 TF32 再快一档，且动态范围同 FP32（无需 GradScaler，代码已正确返回 `None`）。
- ⚠️ RT916 的 `FFT_for_Period` 已做 bf16→fp32 回退（`model.py:15-17`）——**torch.fft 不支持 bf16**，这正确处理了，但意味着 FFT 段在 fp32 下跑，无法用 Tensor Core（FFT 不是 GEMM，本来也用不上，且 96 点 FFT 极小，可忽略）。

### 1.3 cuBLAS workspace / heuristics

- cuBLASLt 用 `cublasLtMatmulAlgoGetHeuristic` 按问题尺寸/数据类型返回候选算法，有 **heuristics cache**（容量可调 `cublasLtHeuristicsCacheSetCapacity`）。[cuBLAS 文档 §3.1.2](https://docs.nvidia.com/cuda/cublas/index.html#heuristics-cache)
- 某些 GEMM 算法（split-K、FP64 定点仿真、3xTF32）需要 **workspace**；`cublasSetWorkspace()` 可让用户提供固定显存，避免运行时 `cudaMallocAsync`。确定性（reproducibility）要求每个 stream 独立 workspace 或设 `CUBLAS_WORKSPACE_CONFIG`。[cuBLAS 文档 §2.4.8](https://docs.nvidia.com/cuda/cublas/index.html#cublassetworkspace)
- **PyTorch 内部已管理 workspace**，框架用户一般无需干预；只有要强制确定性输出时才需要 `CUBLAS_WORKSPACE_CONFIG`，而这会牺牲性能——本项目不需要。
- 结论：heuristics/workspace 属于"透明但不可控"，正常训练不用动；要精细控制应走 cuBLASLt 手工 benchmark（框架层做，PyTorch 已默认做了部分）。

### 1.4 小矩阵 GEMM 的优化要点（本项目的核心问题）

**为什么小 GEMM 是 memory-bound / launch-bound：**

- 算术强度 `AI = M·N·K / (M·K + N·K + M·N)`。[NVIDIA Matrix Multiplication Guide](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html#math-mem)
- 对本项目 `Linear(64,64)`、batch=64：`AI = 64·64·64 / (64·64·3) ≈ 21 FLOP/B`。RTX3090 的 `FLOPS:byte` 比（BF16 下）远高于此 → **memory-bound**。GEMV（N=1）AI<1，永远 memory-bound。
- **tile/wave quantization**：cuBLAS 大矩阵用 256×128 tile（最省带宽），64×64 tile 最不划算；小矩阵只能用小 tile，tile 数又不足以填满 SM（wave quantization），GPU 利用率低。[NVIDIA Matrix Multiplication Guide §3](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html#dim-quantization)
- 对 96 点序列 + 64 隐藏维，还有 **kernel launch 开销**（~2-5μs/次）占比放大问题——训练步里可能有几十个 64×64 GEMM，每个都 launch 一次。

**结论：cuBLAS 默认策略对"大而少的 GEMM"调优充分，对"小而多的 GEMM"不是不够快，而是"快不起来"——瓶颈在访存和 launch，不在算法。** 优化方向只能是：
1. **减少 kernel 数量**（算子融合：`torch.compile` / 手写融合 kernel）；
2. **减少 launch 开销**（CUDA Graph / `reduce-overhead`）；
3. **增大有效 GEMM**（合并 batch / 合并多个 Linear 为一发大 GEMM）；
4. 保持维度为 8 的倍数（64 已满足 Tensor Core 对齐要求，[NVIDIA 要求 FP16/BF16 每维 8 的倍数](https://docs.nvidia.com/deeplearning/performance/dl-performance-matrix-multiplication/index.html#requirements-tc)）。

## 2. CUTLASS

### 2.1 CUTLASS 是什么、解决什么问题

- **定义**：NVIDIA 的开源 CUDA C++ 模板库 + Python DSL，提供分层可定制的 GEMM / implicit-GEMM 卷积 / 融合算子，把 cuBLAS 这种"黑盒"变成"可拆装"（可定制 tile 大小、pipeline、epilogue、数据类型：FP64→FP32→TF32→FP16/BF16→FP8/MXFP4→INT8）。[CUTLASS 文档](https://docs.nvidia.com/cutlass/)
- **它解决的问题**：cuBLAS/cuDNN 是通用最优解，但（a）不可定制 epilogue（如把激活/残差/量化融进 GEMM 尾部）、（b）对特定形状/数据类型没有专精 kernel、（c）难以利用新硬件特性（如 Blackwell tcgen05）。CUTLASS 让工程团队写出"逼近硬件峰值"的专用 kernel。
- 官方定位：在 Ampere 到 Blackwell 上实现峰值性能 GEMM。

### 2.2 "小矩阵多 batch"场景 CUTLASS 是否有优势

- **基本没有优势**。CUTLASS 的价值在大 GEMM 的 tiling/occupancy 优化和 epilogue 融合；本项目 64×64 GEMM 的问题是"访存带宽 + launch 开销"，CUTLASS 手写 kernel 也不能让 memory-bound 的 GEMM 突破访存上限。
- cuBLASLt 已内置多种小 GEMM 变体（含 grouped/batched，见 `cublasGemmStridedBatched`），PyTorch 已经吃到这些。
- 真要优化小矩阵，方向是**合并成更大的 GEMM**（把 3 个 scale 的 `season_mlps` 拼成一个 `(3B,64)×(64,64)`）或 **融合整块算子**，前者用 torch 一行可做，后者用 Triton 比 CUTLASS 省一个数量级的工作量。

### 2.3 CUTLASS vs PyTorch/Triton：用哪个更实际

| 方案 | 上手成本 | 性能 | 适用场景 |
|---|---|---|---|
| `torch.compile`（inductor，后端是 Triton） | 一行 | cuBLAS 的 ~90%+，且自动融合 pointwise/reduction | 通用模型，"免费午餐"，**本项目首选** |
| Triton（手写 `@triton.jit`） | 中等 | 接近 cuBLAS，可定制融合 | 单个热点 kernel 需要融合/定制时 |
| CUTLASS（C++/Python DSL） | 高 | 可逼近硬件峰值 | 生产级大 GEMM、新硬件特性、framework 级算子库 |

- NVIDIA 官方给 CUTLASS Python DSL 的性能定位是"Blackwell 上接近手写 C++（2% 内）"，Hopper/Ampere 为实验特性——**本项目 RTX3090（Ampere）连"最优性能承诺"都拿不到**。
- 推荐路线：**先 `torch.compile(mode="max-autotune")` 白嫖融合 → 若仍有单点热点再考虑 Triton → CUTLASS 留给未来真需要大 GEMM 时**。

## 3. BLAS 层（CPU 侧）

### 3.1 OpenBLAS / MKL / oneDNN 对 CPU 模型的影响

| 组件 | 用的 BLAS 实现 | 本项目影响 |
|---|---|---|
| numpy / scipy（Windows pip 版） | **OpenBLAS**（默认捆绑） | 特征工程、统计计算——**CPU 侧大头** |
| PyTorch CPU | **oneDNN**（原 MKL-DNN）+ 自带算子 | TimesFM PyTorch 后端、SGDFNet（若 CPU 跑） |
| LightGBM | **自带 C++ 多线程实现，不走 BLAS** | BLAS 调优对它**无效**；它只用 `num_threads` |
| xgboost / catboost | 自带实现 + OpenMP | 同上 |
| jax（TimesFM xreg） | XLA（内部 Eigen/oneDNN） | 间接相关，`JAX_NUM_THREADS` 可调 |

- 关键认知：**LightGBM 的 `init_model` warm-start、`num_threads` 与 BLAS 无关**；对 LightGBM 提速靠特征预计算缓存（已计划），不靠 BLAS。
- 特征工程（pandas/numpy 大矩阵运算、shift、groupby）确实吃 OpenBLAS，是 CPU 侧唯一值得碰 BLAS 的地方。

### 3.2 BLAS 线程配置

```
# OpenBLAS（Windows 上也可在代码里设）
OPENBLAS_NUM_THREADS=<物理核数>   # 或 OMP_NUM_THREADS 一并生效
OMP_NUM_THREADS=<物理核数>
MKL_NUM_THREADS=<物理核数>        # 若未来换 intel numpy
OMP_PROC_BIND=CLOSE / KMP_AFFINITY=granularity=fine,compact,1,0
```
- PyTorch CPU：`torch.set_num_threads(n)`，别与 OMP 重复设置。
- **核心陷阱：线程数 × 进程数超配**。项目 DataLoader 默认 `num_workers=4`（`perf_knobs.py`），若同时让 OpenBLAS 用满所有核，会 thrashing。建议 `OPENBLAS_NUM_THREADS / OMP_NUM_THREADS = 物理核数的一半或 `num_workers` 以外的余量`，实际测一条曲线。
- 小矩阵（96 点特征矩阵）BLAS 多线程收益小，**线程调优是锦上添花，不是主菜**。

### 3.3 本项目 CPU 模型能否靠 BLAS 提速

- LightGBM：训练 <0.1s/配置（skill §4.10 实测）——**瓶颈根本不是计算**，BLAS 无意义。
- TimesFM xreg（CPU）：单日 ~98s 零样本（skill §4.13），主成分是 Transformer 前向（memory/launch bound），BLAS 线程调优预计 <10%。
- **结论**：CPU 侧加速主线仍是**特征预计算缓存（单日省 3-7min）+ warm-start**，BLAS 线程配置只是顺手设置即可，不值得深挖。

## 4. 针对本项目的建议

### 4.1 两 GPU 模型的矩阵运算热点（已核验代码）

**TimeMixer（`TimeMixer/backbones.py`）**：
- 大量小 GEMM：`past_proj(features→64)`、`future_proj`、`season_mlps[i]`×3、`trend_mlps[i]`×3、`future_mixer`、`head`（含 `64·(scales+1)=256→64`）。
- 更多是 **memory-bound 算子**：`MovingAvg`（AvgPool1d）、`F.interpolate`（跨尺度上采样）、`LayerNorm`。
- 热点判定：**launch 开销 + 访存 > 算力**。GEMM 本身不是热点，热点是"算子太多、每个太小"。

**RT916（`RT916_SpikeFusionNet/.../model.py`）**：
- `FFT_for_Period`（cuFFT，每层每 batch 一次 rfft）→ 96 点 FFT 极小但 launch 频繁，且含 Python 层 `.item()`/topk 同步。
- `InceptionBlockV1`：**6 个不同 kernel_size 的 Conv2d**（cuDNN implicit GEMM，6 次 launch）→ 可精简。
- `SpikeResidualBranch`：3 个 dilation Conv1d（cuDNN）+ `adaptive_avg_pool1d` + `delta_head` GEMM。
- `DynamicPeriodGate`：FFT 特征 + `Linear(2·128+3,128)` + `Linear(128,pred_len)`。
- 热点判定：**FFT + 小卷积的 launch 频率**是主要开销。

### 4.2 是否值得上 CUTLASS / Triton 定制 GEMM，还是 torch.compile 就够

- **torch.compile 足够，直接上**。理由：
  1. 模型是 memory-bound 小算子堆叠，torch.compile 的**算子融合**（把 GELU+Dropout+残差+LayerNorm 熔成一个 Triton kernel）正是对症下药；
  2. `mode="reduce-overhead"` 用 CUDA Graph 吃掉 launch 开销，对本项目收益比大模型更明显；
  3. Triton（inductor 后端）性能已接近 cuBLAS，无需 CUTLASS。
- ⚠️ **graph break 风险**（本项目主要坑）：
  - RT916 `TimesBlock.forward` 里 `for i in range(period_list.shape[0])` + `.item()`（`model.py:99-100`）→ 数据依赖 Python 控制流，**必 graph break**。
  - `FFT_for_Period` 的 `topk` 返回值被 `.item()` 消费 → break。
  - 处置：用 `torch.compile(..., fullgraph=False)`（自动在 break 处切图，安全），或把 `TimesBlock` 的循环改成 `torch.where`/`torch.cond` 消除 break。先接受 partial graph 收益即可，别为 fullgraph 大动干戈。
- **上 CUTLASS：不值得**（见 §2.2）。若未来某个单点 kernel（如融合后的周期卷积）成为热点，用 Triton 手写即可。

### 4.3 可落地的 3-5 条优化（按性价比排序）

1. **`torch.compile` 包住 backbone（GPU 侧首选，成本一行）**
   - 对 `TimeMixerBackbone.forward` 与 `SpikeGatedTimesNet.forward` 加 `torch.compile(mode="reduce-overhead")`（或先 `"default"` 实测）。
   - 收益：融合 pointwise/reduction + 减少 launch。预计整体 1.2~1.5×（GPU 训练步），风险低（改一行，可环境变量开关）。
   - 注意：固定输入 shape 才能吃满 reduce-overhead 的 CUDA Graph 收益。

2. **固定 batch 形状 + 预热（配合 CUDA Graph）**
   - 训练 loop 前跑 1-2 步 warmup 预热 allocator/编译缓存；batch 固定（不要变长 pad），减少图重编。

3. **合并小 GEMM（TimeMixer 专属，低风险高收益）**
   - 将 3 个 scale 的 `season_mlps`/`trend_mlps` 各自的 `Linear(64,64)` 合并为**一个 `Linear(64·3,64)`** 再切片，把 6 次 launch 变成 2 次、且 GEMM 尺寸变大（AI 提高）。等价改动小，可先只合并 trend/season 各一发。

4. **精简 RT916 的 InceptionBlockV1 与 FFT 开销**
   - 6 个不同 kernel 的 Conv2d 是 6 次 cuDNN launch，且周期维度极小（period≈96/k）；可考虑把 kernel 数从 6 降到 3-4（`num_kernels` 参数）或先用 `torch.compile` 融合。
   - FFT 的 `.item()` 同步点：把 `period_list` 的 Python 循环移到 batch 外/用向量化 topk，消除同步（也顺带消 graph break）。

5. **CPU 侧顺手配置 + 主线加速（不花时间深挖）**
   - 启动脚本统一设 `OMP_NUM_THREADS=物理核数的一半`、`OPENBLAS_NUM_THREADS` 同值，避免与 DataLoader `num_workers=4` 抢核。
   - **主线仍是**：特征预计算 FeatureStore（单日省 3-7min）+ warm-start 续训（3天→1天）——矩阵层优化是补充，不是替代。

6. **（可选）TF32 API 迁移与精度快检**
   - 将 `perf_knobs.py` 的 `allow_tf32` 迁移到新 API `torch.backends.cuda.matmul.fp32_precision = "tf32"`（新老不能混用），并在 GPU 上做一次"开/关 TF32 + BF16 vs FP32"的 SMAPE 对照，确认无精度回退（本项目指标敏感，见 skill §4.9 SMAPE 铁律）。
