## 一、特征预计算：存储规模 / 时间节省 / 运行原理

### 1.1 本地存储多少（量化估算）

| 项 | 96点 | 24点 | 合计 |
|---|---|---|---|
| 源数据行数 | 160,800 | 40,536 | — |
| 特征列数（保守） | ~30 | ~25 | — |
| 特征矩阵（float32） | **19.3 MB** | **4.1 MB** | **23.4 MB** |
| parquet 压缩后 | ~10-15 MB | ~2-3 MB | **~15-20 MB** |
| 内存加载 | 一次性进内存，常驻 | 同左 | **<25 MB** |

> 结论：**本地存储约 15-20 MB（parquet），内存常驻 <25 MB**，可忽略不计（对比源宽表 70 MB）。
> 含 DA/RT 双命名空间 × 2 分辨率 = 4 个矩阵，总存储 <50 MB。

### 1.2 能节省多少时间

**现状瓶颈**：214 天回测 × 7 模型，**每个模型每天自己 read_excel + 自己算 lag/rolling/日历特征**。

| 阶段 | 现状耗时（单日） | 预计算后（单日） |
|---|---|---|
| 模型各自读宽表 + 特征工程 | ~1-3 min × 7 模型（重复劳动） | **~0**（切片是内存操作） |
| 物化特征矩阵（首次） | — | 一次性 ~1-3 min（跑回测第 1 遍） |
| 回测第 2 遍起 | — | **~0**（指纹命中，零重算） |

**收益估算**：
- 单日 17 分钟里，特征工程约占 3-7 分钟（7 模型各自重复算）
- 预计算后：**单日节省 ~3-7 min** → 214 天回测节省 **~10-25 小时**
- 叠加 warm-start（省 GPU 训练 epoch）：**总回测 3 天 → ~1-1.5 天**（与调研报告一致）

> 保守：特征预计算单独立项可省 **30-40%** 回测墙钟；+warm-start 再省 **30-50%**，合计压到 1/3。

### 1.3 运行原理（简单讲）

```
① 首次：FeatureStore.ensure(resolution, source)
   读一次宽表 → 按"特征注册表"一次性算好全部特征（lag/rolling/日历）
   → DA/RT 分两个命名空间存 parquet（含 p56 asof 遮蔽）
   → 写 manifest（数据指纹 + 特征版本）

② 之后每天：scheduler 前调用 FeatureStore.slice(model, task, D)
   → 内存里按日期切一小块 DataFrame 给每个模型
   → 模型只做"归一化 + 训练"，不再碰特征工程

③ 数据更新（爬虫/回填）：源文件指纹变 → 自动重建（或增量追加尾行）
```

**关键**：特征值只算一次，214 天回测每天只是"读切片"——这就是调研报告说的 point-in-time join（一次物化、按时点切片），和 Feast/Tecton 语义一致，只是 60 行轻量实现。

### 1.4 DA/RT 与模型依赖处理（已设计）
- DA/RT **双命名空间**：`feature_store/{res}/da|rt/matrix.parquet`，shift 常量只在注册表一处
- **SGDFNet 两阶段**：先物化 DA + 跑完 DA → 再物化 RT（da_anchor 引用 DA 产物）
- **CPU/GPU 并行**：矩阵在 scheduler 前物化进内存 → 线程池只读切片，天然线程安全

## 二、极端价修正对照实验（V0-V4）

### 2.1 实验思路（按你的要求：不跑全链路，先接几个模型验证）

**为什么先接几个模型**：全链路 7 模型跑 V0-V4 太慢且改动面大。先用**代表性子集**验证"修正公式改法"的方向对不对、放哪里合适、怎么搭配更好，方向对了再全量。

**选型**（代表性 3 模型）：
| 模型 | 选它原因 | 设备 |
|---|---|---|
| **lightgbm (RT)** | CPU 快、有负价钳制逻辑（train_fix.py）、最能代表"漏报"场景 | CPU |
| **sgdfnet (RT)** | 消费 da_anchor、两阶段依赖的代表 | CPU |
| **timemixer (RT)** | GPU 深度模型代表 | GPU |

### 2.2 实验流程（在实验专区）

```
outputs/experiments/classifier_ab/
├── run_ab.py          # 主实验脚本（V0-V4 对照）
├── config.yaml        # p_lo/p_hi/方案开关
├── results/
│   ├── v0_baseline_*.csv   # 每方案：修正后预测
│   ├── metrics_*.csv       # 事件级指标
│   └── summary.md          # 对照汇总
└── logs/
```

**流程**：
1. 取一段历史窗（≥30 完整日，用既有 ledger_96 账本）
2. 跑 3 模型预测 → 融合（复用 BGEW，冻结权重不重学）
3. 对融合结果分别应用 V0/V1/V2/V3/V4 修正公式
4. 对照真实 RT 实际价，算事件级指标（M1-M4 + 事件加权 SMAPE）
5. summary.md 输出对照结论

### 2.3 关键诊断量（回答"放哪里/怎么搭配"）
- **M1** = P(y_fused>100 | y≤-50, p≥θ)：现状门槛挡住真负价比率 → 修正后应→0
- **M2** = P(p≥θ | y≤-50)：分类器自身召回（天花板，先看它够不够高）
- **M3** = 事件加权 SMAPE 相对 V0 变化（负=改进）
- **M4** = 新增误报事件率（修正把正常价错改 -80 的比例）

### 2.4 实验脚本骨架（复用现有链路）

```python
# run_ab.py（骨架）
from pipelines.ledger_predict import run_ledger_predict  # 或直接调 3 模型 adapter
from fusion.apply_daily_ledger_weights import apply_weights  # 融合
from ExtremPriceClf... import get_final_prob                 # 分类器 p
from fusion.classifier_bridge import soft_correct            # 新公式

SCHEMES = {
    "v0": lambda p,yf: -80 if (p>=0.55 and yf<=100) else yf,   # 现状
    "v1": lambda p,yf: -80 if p>=0.55 else yf,                 # 硬前置
    "v2": lambda p,yf: yf + h(p)*(-80-yf),                     # 软修正(无门槛)
    "v3": lambda p,yf: v2 + (-80 if p>=0.80 else 0),           # 混合+兜底
    "v4": lambda p,yf: v2 + (-80 if (p>=0.55 and min_m<=30) else 0),  # 一致性
}
# 每方案跑同一批预测 → 算事件级指标 → 输出对照
```

### 2.5 判定标准
- 若 M1 显著↓ 且 M3 事件加权 SMAPE 改善、M4 误报不恶化 → **修正公式采纳**
- 若 V2/V3 明显优于 V0/V1 → 选软修正方向；V4 优于 V3 → 加一致性门
- 结果写入 summary.md + 更新 skill（含 p_lo/p_hi 最佳取值）
