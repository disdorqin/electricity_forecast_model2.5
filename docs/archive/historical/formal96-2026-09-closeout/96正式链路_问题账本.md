## 2. P0：split_process 当前不是目标 CPU DAG

### 2.1 已确认事实

当前 `split_process`：
- CPU 子进程与 GPU 子进程会同时启动，CPU/GPU 真并行这一点正确；
- GPU 子进程严格串行，符合单 GPU 稳定性要求；
- CPU 子进程当前也被写死为严格串行：`max_cpu_workers=1`；
- `_split_queue_entry()` 内部再次构造 `ResourceScheduler(max_cpu_workers=1, max_gpu_workers=1)`。

因此外部传入的 `--max-cpu-workers` 在 split_process CPU 子进程里目前不会产生并行效果。

### 2.2 用户冻结的目标 DAG

CPU 逻辑链：

```text
TimesFM DA → TimesFM RT
SGDFNet DA/anchor prepare → SGDFNet RT
LightGBM DA
```

用户提出的串行书写顺序为：

```text
TimesFM DA → TimesFM RT → SGDFNet DA → SGDFNet RT → LightGBM DA
```

但从依赖关系看，三条 CPU 支路不是必须彼此串行。后续应保持相同业务依赖，同时允许独立支路并行。

GPU 逻辑链：

```text
TimeMixer DA → TimeMixer RT → RT916 DA → RT916 RT
```

其中 RT916 当前生产 adapter 已在单个 `rt916/realtime` 任务内部执行 joint DA→RT：
`run_joint_da_rt_daily_backtest()` 先产 DA，再注入 RT。因此“RT916 DA→RT”在算法上已存在，不必为了目录形式额外把 RT916 DA 加入正式 DA 三模型池。

### 2.3 当前错误/多余依赖

当前 unified plan 中：
- `TimesFM RT ← TimesFM DA`：按用户正式设计保留；
- `TimeMixer RT ← TimeMixer DA`：按用户正式设计保留；
- `SGDFNet RT ← TimesFM DA`：错误，应改为 SGDFNet 自己的 DA/anchor prepare；
- `RT916 RT ← TimeMixer RT`：错误，RT916 自身 joint DA→RT，不应被 TimeMixer 失败级联阻断。

### 2.4 CPU 并行的实现风险

旧 `_run_queue(max_workers>1)` 不是 DAG-aware：它会一次性 submit 全部 task；task 只在启动时检查 dependency 文件。因此直接把 split_process 的 `max_cpu_workers=1` 改成 2/4 可能让子任务在父任务尚未落盘时立即失败。

**结论：CPU 并行必须通过“依赖就绪后才 submit”的 DAG scheduler 实现，不能只改 worker 数。**

### 2.5 max_cpu_workers 当前建议

基于 2026-08-16 本机耗时：
- TimesFM DA ≈14.1s，RT ≈10.9s，链路约25s；
- SGDFNet RT ≈8.0s；
- LightGBM DA ≈6.5s。

理论上两条 CPU worker 已足以把独立的 SGDFNet/LightGBM 工作隐藏在 TimesFM DA→RT 约25s关键路径内。第三 worker 对当前三支路的 wall time 理论收益很小，却增加 BLAS/JAX/LightGBM 线程争用。

用户于 2026-09-18 确认采用该方案：**正式 CPU DAG 目标为 `max_cpu_workers=2`，实现必须 DAG-aware；服务器仍保留 W1=1 vs W2=2 最小 A/B 作为验收证据，暂不考虑 3+。**

执行 AI 修改时必须依据代码图做关联修改，不允许只改 scheduler 单点。至少同步检查：`runtime/resource_scheduler.py`、`pipelines/ledger_predict.py`、`fusion/model_pool.py`、相关 adapter、server benchmark/audit 与 tests。完成后先跑最小测试：DAG 单元/调度 smoke + `--predict dayahead/realtime/both` task-scope smoke，再进行重模型完整运行。

## 3. P0：SGDFNet 业务 anchor contract 未按正式口径实现

### 3.1 正式业务口径

用户再次确认并冻结：

```text
今天（decision day）预测明天 target D 的 RT
SGDFNet da_anchor 只能使用“今天”的完整日前 96 点
即 source_day = D-1
按 p1...p96 对齐到 D
```

这里“只能用当天”指预测当下这一天/decision day 的日前，**禁止使用 target D 当天的日前值作为 SGDFNet anchor**。该条业务规则不等待明日信息边界会议确认；其他字段边界仍待确认。

### 3.2 当前代码行为

SGDFNet 核心当前：
- 直接令 `da_anchor = 当前行 日前电价`；
- 若 NaN，则使用历史同小时 median fallback；
- 2026-08-16 运行时 target-day 日前被统一 as-of mask，导致 96/96 anchor NaN，实际走了 median fallback。

这不符合正式业务 contract。

### 3.3 2026-08-16 是否泄露

**直接 target truth 泄露：未发现。**

证据：
- as-of audit 对 2026-08-16 target-day `日前电价/实时电价/actual_*` 全部 mask；
- （历史固定 cutoff 记录，**SUPERSEDED FOR FORMAL 96**）D-1 RT/actual 只保留至 p60（15:00）；当前 formal serving 由 Dynamic-v1 snapshot/FeatureView 路由。
- SGDFNet target anchor 因被 mask 而使用历史同小时 median，不是 target-day realized DA；
- SGDFNet 历史 delta/actual 相关特征使用 resolution-aware lag，未直接回流 target-day RT/actual。

因此 SGDFNet 的 8/16 问题是 **业务 anchor 用错/降级**，不是“偷看了 8/16 实时真值”。

但整个历史 8/16 replay 仍不能标为完整 STRICT historical evidence：旧历史 forecast 字段的 D-1 vintage 未有独立快照证明，属于 forecast-vintage provenance 未确认。应区分：
- realized leakage wall：PASS；
- SGDFNet anchor business contract：FAIL/DEGRADED；
- historical forecast vintage：UNVERIFIED。

## 5. P0：正式模型池固定，但 split task 过滤实现有误

正式模型池已由用户再次确认：
- DA 固定：`lightgbm, timesfm, timemixer`；
- RT 固定：`timemixer, timesfm, rt916, sgdfnet`（顺序不代表依赖）。

工程上不应在多处重复“硬编码”列表；继续以 `fusion/model_pool.py` 作为唯一生产模型池来源，相当于**固定生产配置**。真正需要修的是 unified plan 的 task-node 选择逻辑。

### 当前语义错误

当前 `_run_unified_model_plan()` 使用：

`selected = set(selected_da_models) | set(selected_rt_models)`

随后只按 `model_name` 判断 ordered task 是否入队，而不是按 `(model_name, task)` 判断。

影响：
- `target=dayahead` 时，TimesFM/TimeMixer 与 RT 共用模型名，split plan 可能把它们的 realtime task 也加入；
- `target=realtime` 时，TimesFM/TimeMixer 的 DA task 也可能被带入。后者部分可解释为依赖，但必须由显式 DAG dependency 决定，不能依赖模型名碰巧相同。

完整 `target=both` 时不明显，但用户冻结的新 `--predict dayahead|realtime` 会直接暴露这个问题。

要求：统一按 task-node identity `(model, task/internal_node)` 构建 DAG，不能再用模型名并集筛 task。

## 8. P1：RT916 production stride 已冻结为24，尚待代码生产化

当前 RT916：
`TRAIN_STEPS = int(os.getenv("RT916_TRAIN_STEPS", "1"))`

代码 `ElectricityDataset` 实际使用：
`for i in range(0, len(data) - seq_len + 1, step)`。

因此它**不是训练 epoch/gradient step 数**，而是训练样本滑窗的 stride：
- `1`：每个 15min 都生成一个训练窗口，样本最密、训练最慢；
- `24`：96 点数据上每 24 个槽取一个窗口，即约每 6 小时取样一次，训练样本量约降至 1/24；
- 更大的 stride 会继续加速，但同时改变训练样本分布，因此不能仅视为性能参数。

历史实测：
- 默认 1 时 96 点单日曾出现约30分钟级慢运行；
- `RT916_TRAIN_STEPS=24` 时 GPU 单日约151s。

现有 2026-08 本机三个月窗扫参已经给出有效边界：`1 → 24 → 96` 中，24 显著提速且精度仍可接受，96 已明显退化（历史记录：24 的 SMAPE 约 0.23~0.32，96 约 0.45~0.82）。

用户于 2026-09-18 已正式裁决：**生产链路固定 `RT916_TRAIN_STEPS=24`，本轮不再继续 stride sweep。**

当前剩余问题仅是生产化：正式 `--96` façade 必须内部显式使用24并写入 manifest，不能依赖部署 shell 环境；internal/experiment 入口可以继续允许显式 override，但不得污染 production façade。
