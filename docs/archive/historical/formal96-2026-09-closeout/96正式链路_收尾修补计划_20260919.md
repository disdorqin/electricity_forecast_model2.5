## 2. 调度测试闸门：放宽总耗时，不放宽并发正确性

### 2.1 发现

`scripts/tests/check_split_resource_scheduler.py` 当前包含：

```python
assert elapsed < 20.0
```

独立审查中出现过一次：

```text
elapsed = 24.025s
```

导致假红。

随后连续复跑 5 次全部 PASS；另外 3 次外层 wall-time 测量：

```text
13.892s
13.987s
12.816s
```

功能性硬门在 elapsed 判断之前已经验证：

- CPU 两个 independent ready nodes 启动时间差 < 0.15s；
- CPU/GPU 首任务启动时间差 < 1.0s；
- GPU parent-before-child 严格串行；
- CPU parent-before-child 正确；
- failed dependency 只阻断 descendant；
- unrelated node 继续执行。

因此 20s 不是正确性的核心，只是 Windows spawn watchdog。

### 2.2 正式修法

把：

```python
assert elapsed < 20.0
```

放宽为：

```python
assert elapsed < 35.0
```

理由：

- 正常观测约 12.8–14.0s；
- 已观测偶发值 24.0s；
- 35s 对已知 outlier 留出约 46% 余量；
- 仍能阻止明显 spawn hang；
- 真正并发正确性继续由 timestamp assertions 严格控制。

同时更新测试注释，明确：

> elapsed 是 Windows spawn watchdog，不是 speed benchmark；并发正确性以事件时间戳为唯一硬证据。

修改后至少连续运行 5 次，必须 5/5 PASS。

## 7. 发现 B：full run 外部中断后根 manifest 可能继续显示旧 complete

### 7.1 实际观察

在启动完整命令前，`outputs/96/runs/2026-08-16/run_manifest.json` 是历史 TimesFM-only prediction manifest：

```text
pipeline=ledger_predict
status=complete
requested_tasks=[realtime]
selected_model_pool=realtime:[timesfm]
```

完整命令运行超过 300s 被外部终止后：

- 新的 LightGBM DA / TimesFM DA 已经落盘；
- 新 scratch 已产生；
- 但根 `run_manifest.json` 仍保持旧 TimesFM-only `status=complete`。

因此“文件内容属于新 attempt，manifest 却属于旧 attempt”。

### 7.2 根因方向

- `ledger_full` 开始时只在内存构造 `status=running`，没有立即写 root manifest；
- `ledger_predict` 自己只在结束时写同一个 root `run_manifest.json`；
- full 和 child stage 共享一个 manifest 文件所有权；
- 外部 kill 发生在 child 未完成时，旧 manifest 不会被覆盖。

### 7.3 修法

formal full orchestrator 必须成为 root manifest 唯一 owner：

1. full run 开始即原子写：
   - `pipeline=ledger_full`
   - `attempt_id`
   - `status=running`
   - `started_at`
   - production config
   - `stages.ledger_predict.status=running`
2. 每个 Stage 完成/失败立即原子更新；
3. embedded `ledger_predict` 不得覆盖 root manifest；
4. prediction stage 若需要独立记录，写 stage-specific manifest 或仅 return dict；
5. KeyboardInterrupt / 可捕获异常写 `status=interrupted/failed`；
6. 无法捕获的外部 kill 至少留下当前 attempt 的 `running`，不能留下旧 `complete`。

同日 rerun 时还需：

- 为新 attempt 清除/隔离旧 `final/submission_ready.csv`、delivery report、fallback report；
- prediction cache 可以保留，但必须逐模型重新验证 provenance/96槽后才能 reuse；
- 不允许“旧 final 文件存在”被新 attempt 误认作当前输出。

## 9. 发现 D：strict cold-start fail-closed 与 emergency fallback 当前冲突

### 9.1 实际结果

上述 `--finish` 在 weight 失败后，当前 `ledger_full` 自动执行：

```text
historical_same_hour_median emergency fallback
```

最终：

```text
delivery_status = DEGRADED_DELIVERED
exit_code = 2
postflight = PASS
submission_ready.csv = 96 rows / 0 NaN
```

真实 fallback 文件：

```text
business_day, ds, business_period, period, dayahead_price, realtime_price
96 rows
0 NaN
```

因此它不是“伪 NORMAL”，但它会在 strict production history 不满足时仍产生一个看起来完整的正式文件。

### 9.2 风险

当前问题账本写：

```text
fail_closed_no_legacy_invalid_ledger_fallback
```

但最终 orchestration 实际仍会 emergency fallback。

如果前端/人工只看：

```text
submission_ready.csv exists
```

而忽略 exit 2 / DEGRADED，则可能误把历史中位数当正式模型预测。

### 9.3 本修补计划建议的正式规则

formal 96 对以下**契约/冷启动类失败**必须严格 fail-closed：

- `INSUFFICIENT_STRICT_HISTORY`
- `INCOMPLETE_PREDICTION_PROVENANCE`
- formal model pool/schema mismatch
- invalid as-of/leakage gate
- wrong RT916 production config
- SGDFNet anchor contract fail

这些情况：

- 不调用 emergency fallback；
- 不新建 `submission_ready.csv`；
- 清除/隔离同 target 的 stale submission；
- `delivery_status=FAILED_NO_DELIVERY`；
- exit=1。

24 legacy emergency fallback 保持不变。

formal 96 是否未来允许显式 `--allow-degraded-fallback`，另立运维策略讨论；本轮不默认开放。
