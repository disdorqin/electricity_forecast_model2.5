# 24点硬编码与模型入口一致性审计

> status: active

> 审计日期：2026-08-16
> 审计范围：生产主链路、交付校验、账本权重学习、模型适配器和现有测试脚本
> 审计依据：当前工作树代码、`git grep` 静态检索、已有回归脚本

## 1. 结论摘要

当前项目的**生产主链路已经具备分辨率参数**，但存在三类一致性问题：

1. 模型池在多个文件重复声明，容易出现主链路、权重学习、交付校验不一致。
2. 生产入口的 24 点硬编码已经部分参数化，但 `verify_final_pipeline.py`、smoke 检查、旧审计脚本仍有大量 24 点假设。
3. LightGBM 适配器仍然接受 `target="realtime"`，即使当前业务不把它放入 RT 候选池，未来仍可能被误调用；TimesFM RT 是正式候选，不能误禁用。

本次审计后采取的原则是：

- 日前模型池：`lightgbm + timesfm + timemixer`；
- 实时模型池：`timesfm + sgdfnet + timemixer + rt916`；
- LightGBM 的 RT 入口保留适配器文件，但明确抛出“非生产候选模型”错误，不允许静默运行；TimesFM RT 正常进入生产候选池；
- 所有生产代码从单一模型池模块读取候选模型；
- 24/96点数量统一从 `utils/resolution.py` 推导；
- `_archive/` 和明确标记为历史的材料不纳入生产一致性审计。

## 3. LightGBM RT入口与TimesFM RT正式入口

### 当前可达路径

- `pipelines/ledger_predict.py` 的通用 `_predict_model()` 支持 LightGBM/TimesFM，但 LightGBM RT 被生产入口阻断，TimesFM RT 正常保留。
- `runners/adapters/lightgbm_v1.py` 的 `target_map` 同时包含 `dayahead` 和 `realtime`。
- `runners/adapters/timesfm_v1.py` 将 `target="realtime"` 映射到正式 TimesFM RT。
- `fusion/run_fixed_window_fusion.py` 和 `fusion/pipeline_common.py` 仍保存TimesFM RT实验接口。

### 处理原则

LightGBM 仍可用于 DA，但不允许作为生产 RT 候选模型。TimesFM 同时用于 DA 和 RT。LightGBM 适配器入口不直接删除，改为：

```python
if target == "realtime":
    raise ValueError(
        "lightgbm realtime path is disabled: "
        "not in the production realtime candidate pool"
    )
```

这样既不会破坏历史代码文件，又能防止未来误调用时静默产生结果。

## 4. 24点硬编码审计

### 需要参数化的生产/验证代码

| 文件 | 风险 |
|---|---|
| `pipelines/ledger_smoke.py` | 72/96行数直接写死，96点smoke会误判 |
| `scripts/tests/verify_final_pipeline.py` | 模型行数、融合行数、训练行数、分类器行数、提交行数均按24点写死 |
| `pipelines/ledger_full_range.py` | 文档和部分校验仍使用24点描述，需要继续核对运行分支 |
| `fusion/learners/daily_ledger_gef.py` | coverage说明和小时粒度使用24点假设，核心计算已部分参数化 |
| `scripts/audit_30day_backfill.py` | 主要是24点审计工具，应显式标记hourly-only，不能误用于96点 |
| `scripts/tests/check_delivery_stability.py` | 合成测试是24点专用，应增加resolution参数或明确标注 |
| `scripts/tests/check_timemixer_alignment.py` | 目前是24点对齐检查，96点应使用独立检查器 |

### 可以保留的24点常量

以下不是问题，而是业务语义或兼容性定义：

- `Resolution(label="hourly", slots_per_day=24)`；
- `hour_business=1..24` 的24点输出契约；
- 24点专属的`1_8/9_16/17_24`时段标签；
- 24点历史数据源字段和提交列。

关键区别是：**24必须只出现在Resolution、业务契约或hourly-only脚本中，不能散落在通用生产逻辑里。**

## 5. cutoff入口审计

### 当前统一入口

`cli/parser.py` 默认 `--realtime-cutoff-hour 14`，`pipelines/ledger_predict.py` 会将其下发给：

- TimeMixer；
- SGDFNet；
- RT916。

### 非统一入口

以下文件仍存在15:00历史默认值或独立调用入口：

- `RT916_SpikeFusionNet/src/rt916_spikefusionnet/core.py` 的独立回测默认值；
- `SGDFNet/src/sgdfnet/protocol_b_cutoff.py` 的历史默认值；
- TimeMixer若干单任务/协议脚本中的旧15:00默认值；
- LightGBM RT适配器中的旧截止计算逻辑。

这些入口不一定被`main.py`生产链路调用，但名称和默认值容易造成误用。处理方式不是删除历史实验，而是：

1. 生产入口只接受统一的`cutoff_ts`/`realtime_cutoff_hour`；
2. 独立入口若保留，必须命名为`legacy_backtest`或显式要求传入cutoff；
3. 默认值不再使用15:00；
4. 所有输出manifest记录`cutoff_hour=14`和96点下的`last_visible_period=56`。

## 6. 自动化信息可得性方案

建议分三层实施，不一次性重写所有模型：

### 第一层：统一预测上下文

新增只读对象：

```text
ForecastContext(
    target_day,
    task,
    resolution,
    decision_ts,
    cutoff_ts,
    target_columns
)
```

所有模型适配器接收同一个上下文，不再各自计算 cutoff。

### 第二层：特征来源注册表

每个特征声明：

```text
feature_name
source_table
source_role: forecast / actual / target / lag
available_from
allowed_lag
allowed_tasks
```

示例：

```text
actual_wind:
  role=actual
  allowed_use=history_lag_only

fcast_wind:
  role=forecast
  allowed_use=dayahead,realtime

rt_cq_price:
  role=target
  allowed_use=label_or_history_lag
```

### 第三层：运行前自动审计

在每个模型推理前自动执行：

1. target day的`actual_*`是否被直接使用；
2. cutoff之后的RT列是否仍有非空值进入特征；
3. `data_cutoff`是否不晚于`cutoff_ts`；
4. lag特征是否至少经过正确的24/96槽位shift；
5. 数据源是否与分辨率匹配；
6. 模型输出manifest是否记录特征审计结果。

发生违规时应直接阻断该模型，并写入：

```text
run_manifest.json
delivery_report.md
model_availability_audit.json
```

这比依靠人工阅读代码更适合长期维护。第一阶段建议先做“静态注册表+运行前断言”，不要立刻改写所有模型内部特征工程。

## 7. 本次整改优先级

1. 统一生产模型池，禁用LightGBM RT入口，保留TimesFM RT正式候选；
2. 修复`verify_final_pipeline.py`和smoke检查的24点硬编码；
3. 将cutoff统一到`ForecastContext`；
4. 增加模型权重质量门控；
5. 固定requirements和TimesFM依赖；
6. 清理并归档agent研究文档；
7. 再推进自动化信息可得性注册表。
