# 05 模型与训练流程

## 1. 当前审查包的模型结构

本包当前主模型是三个独立的 LightGBM 回归器：

```text
1_8   -> LGBMRegressor
9_16  -> LGBMRegressor
17_24 -> LGBMRegressor
```

每个模型输出对应时段的连续 `DA-RT` 价差。

方向由：

```text
predicted_spread > 0
```

得到。

这条链路的优点是透明、快、容易复现，适合作为后续所有复杂方法的统一基线。

---

## 2. 每一个目标日都是独立滚动预测

对每个目标日 `D`：

```text
forecast origin = D-1 14:00
training_last_day = D-2
training window = 最近180个完整历史日
```

然后分别对三个时段拟合模型并预测 D 日。

伪代码：

```python
for target_day in evaluation_days:
    train_last = target_day - 2 days
    train_first = train_last - 179 days

    for period in [1_8, 9_16, 17_24]:
        X_train, y_train = rows in [train_first, train_last] and period
        X_test = target_day rows of same period
        fit model
        predict target_day
```

这不是“一次训练一个模型然后预测所有月份”，而是 rolling retraining。

---

## 3. 为什么不是随机切分

随机 train/test split 会破坏真实业务顺序，例如：

```text
训练集包含7月
验证集却包含5月
```

这样的结果无法代表真实部署。

本任务所有模型选择、阈值、校准、ensemble 都必须尽量遵守 chronological / walk-forward 原则。

---

## 4. 当前独立包参数

`config.yaml` 当前参数：

```text
objective = regression_l1
n_estimators = 220
learning_rate = 0.03
num_leaves = 31
min_child_samples = 20
subsample = 0.9
colsample_bytree = 0.9
reg_lambda = 1.0
seed = 20260828
training_days = 180
```

注意：这是 **独立审查包的固定配置**。

原 Cycle88 研究 runner 曾使用过略有差异的一组树参数，例如：

```text
n_estimators = 220
learning_rate ≈ 0.035
num_leaves = 31
min_child_samples ≈ 35
subsample = 0.90
colsample_bytree ≈ 0.85
reg_lambda ≈ 2.0
```

因此本包不能宣称“逐参数精确复刻 Cycle88”。

---

## 5. 缺失值处理

当前 pipeline 对每个滚动训练 slice 单独做：

```text
train: median(train) -> remaining NaN = 0
test : median(train) -> remaining NaN = 0
```

这很重要，因为测试日不能参与训练期 median 的计算。

---

## 6. 三段模型为什么保留

Cycle88 早期全局单模型表现出明显的方向偏置和时段差异。

三段结构通过将：

```text
凌晨/早间
光伏主导白天
晚间
```

分开建模，使每个树模型只学习相对同质的状态。

Cycle88 严格跨月对照中，segmented 方案相对此前全局 numeric_v2 在 Raw、Balanced 和 negative recall 上都有小幅改善，因此被选作当前透明基线。

但该提升只有约 1-2 个百分点量级，远不足以达到 70%。这说明 segmentation 是局部优化，不是最终答案。

---

## 7. 当前训练损失与业务指标存在错配

现有回归器优化：

```text
L = |pred_spread - true_spread|
```

但业务关心：

```text
sign(pred_spread) == sign(true_spread)
```

因此当前模型可能出现：

- 数值误差不大但方向错；
- 正类预测过多；
- MAE checkpoint 看起来合理，但 Balanced 仍接近 50%；
- 少数类 recall 低。

这正是老师建议新增二分类 LightGBM 的原因。

---

## 8. 下一阶段方向-幅值解耦

后续建议保持同一输入、同一训练日、同一 period，只改变 target formulation。

### 8.1 Direction Head

```text
X -> LGBMClassifier(objective=binary)

y_dir = 1(Spread > 0)

output = P(Spread > 0)
```

第一阶段先用默认 binary，随后再独立对照：

```text
is_unbalance=True
class_weight / scale_pos_weight
```

禁止第一轮把所有 balancing、calibration、threshold 一次叠上去，否则无法知道提升来自哪一项。

### 8.2 Magnitude Head

```text
X -> LGBMRegressor

y_mag = abs(Spread)
```

最终：

```text
pred_spread = predicted_sign * predicted_magnitude
```

该方案的目的是真正做到：

```text
方向模型只负责方向
幅值模型只负责幅值
```

历史 Cycle88 已经做过一轮干净的 Direction-Magnitude 对照：默认 0.5 分类头并未稳定优于 signed regression，说明“简单拆 target”本身不是银弹；后续才有理由继续测试类别不平衡和决策层。

---

## 9. 类别不平衡实验应该怎么做

建议至少比较：

```text
D0 default binary classifier
D1 is_unbalance=True
D2 explicit class_weight / scale_pos_weight
```

每个 variant 必须：

- same training rows；
- same features；
- same seed；
- same period split；
- threshold 第一轮固定 0.5；
- 不改 calibration。

这样才能回答：

> 少数类表现差，是因为训练 objective 偏置，还是因为特征本身缺少可分信息？

Cycle88 已完成 `is_unbalance=True` 的 selection 级实验：overall Raw 约从 56.12% 到 56.45%，Balanced 从 54.31% 到 54.87%，negative recall 提升约 1.92pp，但幅度很小且两个月不完全一致，因此该结果属于“弱正信号/未晋级”，不能宣称突破。

---

## 10. 概率、校准和阈值属于决策层，不属于模型本体

分类器输出：

```text
p = P(Spread > 0)
```

默认：

```text
p >= 0.5 -> positive
```

但后续可以在历史 OOS 预测上：

1. 检查概率是否校准；
2. 做 Platt scaling；
3. 搜索 threshold；
4. 比较固定阈值与动态/分时段阈值；
5. 评价稳定性。

这些都必须使用 walk-forward OOS 结果，不能看测试月答案后再调。

---

## 11. 训练与评价必须分层

一个完整实验至少分：

```text
M0 静态/合同审计
M1 smoke（只检查代码和输出）
M2 selection
M3 confirmation
M4 final holdout / lockbox（如果预注册）
```

Smoke 只证明：

```text
代码能跑
24点完整
概率合法
时间边界合法
```

不能因为 smoke 两天成绩高就宣布模型有效。

---

建议逐点预测至少包含：


---

## 13. 模型公平比较规则

后续 LightGBM / CatBoost / TabPFN / TabM 等 benchmark 必须做到：

```text
同一 target
同一特征
同一训练样本
同一评估日期
同一信息边界
同一指标
```

不允许：

```text
A模型用F0-F9
B模型额外看D日actual
然后比较谁分高
```

也不建议第一轮同时让每个 backbone 各自搜索完全不同的数据窗/特征，否则模型比较失去解释性。

---

## 14. 当前模型链路的正确定位

本审查包当前 LightGBM 不是“最终模型”，而是一个：

```text
fast
transparent
auditable
strict-time
strong-enough baseline
```

后续所有新模型首先要证明：

> 在同一严格协议下，真的比这个基线稳定更好。

如果复杂模型只在某几个开发日更好、跨月回落，就不应因为模型名字更新而晋级。
